## What each check verifies


- **Outcome:** the report's `outcome` matches the expected diagnosis.
- **Citations:** exactly the expected evidence IDs are cited. The decoy records are never cited: unrelated requests `E12`, `E29`, `E39`; out-of-window readiness checks `HC16`, `HC35`; check of another service `HC19`; and `HC10`, which the agent should never reach in the 400 case.
- **Tool calls:** the agent calls the expected tools, in order. The 400 case stops after reading the Gateway logs.
- **Evidence removal:** removing `E22`, `HC17` and `HC18` from the outage case changes the diagnosis to `insufficient_evidence`, and the report still cites `E21`.
- **Replay:** the two scenarios look identical in the existing logs. Only `handler_entered` tells them apart, so it scores 1 and the others score 0. Replay assumes candidate events are observed reliably (see `support/replay/ground_truth.json`).
- **LLM agent:** the model's outcome matches the expected diagnosis, every citation comes from a record
  a tool returned in that run, the citations match the rule-based diagnosis, and the model only looked
  at services the case needed (for the 400 case, only the API Gateway), its summary does not claim
  a cause for a timeout or failure, and for insufficient evidence its summary names no failure location
  and its `next_record` asks for a record from the right service.

## What went wrong during development

Earlier runs failed, and the checks caught each failure:
- The model wrote citations itself, sometimes leaving out supporting records and once citing a timestamp as an ID. Citations are now taken from the records the model actually saw.
- The model treated the dependency map as proof and skipped the Order Service logs. It now has to read the logs of each service the request reached before it can finish.
- After checking health status, the model reconsidered and changed a correct `inventory_failure` to `insufficient_evidence`. The prompt now says to weigh all evidence seen so far.
- The model's outage summary said the request failed "likely due to the service being unhealthy". The evidence shows where the request failed, not why, so the earlier guardrail rejected that summary and asked the model to rewrite it. The current agent generates the summary from observed evidence. An invalid request is exempt, because the validation error records the missing field.
- In both insufficient-evidence cases, every check passed but reading the output showed two gaps. `next_record` held an ID the model had already seen (`E31`, `E21`) instead of describing the missing record. One summary also called Inventory "the likely failure location" although the outcome was insufficient evidence. The current agent constructs the summary and next record from observed evidence and checks both during verification. The lesson: passing checks only prove what the checks test, so the output still has to be read.
